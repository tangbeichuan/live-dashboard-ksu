## 1. 项目目标与最终效果

### 目标

- **公开展示**"此刻正在用什么"：朋友访问一个网址即可看到当前状态，不用来问"在不在"
- **隐私优先**：只公开"在用什么应用"的聚合信息，窗口标题、聊天内容、音乐、金融类应用等按分级处理
- **健康数据**：把小米手环的心率/睡眠/血氧/体重同步到面板（按日期查看）
- **可控**：随时能一键进入"隐私模式"，什么都只显示"隐私模式"
- **纯 IPv6 对外**：家宽没有公网 IPv4，全部走 IPv6 + HTTPS

### 最终效果

| 能力 | 状态 |
|---|---|
| 公网 HTTPS 访问（IPv6） | ✅ `https://example.dynv6.net`（Let's Encrypt，DNS-01 自动续期） |
| 手机 App 活动实时上报 | ✅ 前台应用变化即报，5 秒轮询 / 60 秒心跳 |
| 多设备 | ✅ 每台设备独立 token + 独立卡片 |
| 健康数据（步数/心率/睡眠/血氧/体重/身高） | ✅ 每 5 分钟上报，按日期浏览 |
| 隐私模式（手动 / 按 App / 超时） | ✅ 模块 v1.7 |
| 限流 + 扫描器拦截 | ✅ nginx 层 |
| 备份 | ✅ 服务端 + 手机模块双份，含哈希校验 |

## 4. 部署实录（从零到上线）

> 记录踩过的坑，方便日后重装或迁移。

### 4.1 网络前置：为什么只能走 IPv6

- 家宽给的公网 IPv4 实为运营商 NAT，**入站不可能**；IPv6 是真正的公网地址
- ddns-go 初始配置是 `gettype: netInterface`，把**内网地址 192.168.1.100** 当公网 IP 发布到了 dynv6（于是域名解析到内网，外网完全不通）
- **修复**：ddns-go 配置里 `ipv4.enable: false`（关闭 IPv4 发布），IPv6 保持 `netInterface`（直接发布本机全局 IPv6）
- 路由器侧需放行入站 IPv6（关闭 "IPv6 防火墙" 或为设备加放行规则）
- ⚠️ dynv6 的 zone 级 `ipv4address` 字段**无法通过 API 置空**，最后设成 `0.0.0.0`（客户端会立刻失败并回落 IPv6）。想彻底删掉需在 dynv6 网页面板清除

### 4.2 依赖安装（GitHub 被墙的绕法）

| 需求 | 常规做法 | 本项目做法 |
|---|---|---|
| 取源码 | `git clone github.com/...` | ❌ github.com:443 超时；改从 **codeload.github.com** 下 tarball（该域名可达） |
| 装 Bun | `curl -fsSL https://bun.sh/install \| bash` | 安装脚本会去 GitHub Releases 取二进制（被墙）；改为 **`npm install -g bun`**（走 registry.npmjs.org，可达） |
| 证书 | `certbot --nginx`（HTTP-01） | 入站 80 不可靠 → 走 **DNS-01**（dynv6 API） |
| 其他 | — | `apt-get install -y nodejs npm nginx certbot python3-certbot-nginx` |

### 4.3 源码与构建（对应 Dockerfile 的两阶段，但不使用容器）

```bash
# 1) 取源码（codeload 可达）
mkdir -p /opt/live-dashboard && cd /opt/live-dashboard
wget -O main.tar.gz https://codeload.github.com/Monika-Dream/live-dashboard/tar.gz/refs/heads/main
tar xzf main.tar.gz --strip-components=1

# 2) 前端：Bun 装依赖 + Next.js 静态导出
cd packages/frontend
bun install --frozen-lockfile
bun run build            # 产出 out/（Next output: "export"）

# 3) 后端：把前端产物交给 Bun 后端当静态目录
cd /opt/live-dashboard
rm -rf packages/backend/public && cp -r packages/frontend/out packages/backend/public
cd packages/backend && bun install --frozen-lockfile   # 后端零运行时依赖
```

### 4.4 后端 systemd 服务

`/etc/systemd/system/live-dashboard.service`：

```ini
[Unit]
Description=Live Dashboard (Bun backend)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=<用户名>
Group=<用户名>
WorkingDirectory=/opt/live-dashboard/packages/backend
EnvironmentFile=/etc/live-dashboard.env
ExecStart=/usr/local/bin/bun run src/index.ts
Restart=always
RestartSec=3
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

环境变量文件 `/etc/live-dashboard.env`（`root:<用户名> 640`）：

```sh
HASH_SECRET=<openssl rand -hex 32>          # 必须；窗口标题 HMAC 去重哈希用
DEVICE_TOKEN_1=<token>:pc-win:我的电脑:windows
DEVICE_TOKEN_3=<token>:phone-b:手机B:android
DEVICE_TOKEN_4=<token>:phone-a:手机A(root):android
DISPLAY_NAME=<用户名>
SITE_TITLE=<用户名> Now
SITE_DESC=<用户名> 此刻正在做什么？
PORT=3000
STATIC_DIR=/opt/live-dashboard/packages/backend/public
DB_PATH=/opt/live-dashboard/data/live-dashboard.db
CUSTOM_MAPPINGS_FILE=/opt/live-dashboard/data/custom-mappings.json
```

> `DEVICE_TOKEN_N` 的格式是 `token:device_id:显示名:platform`，platform ∈ `windows/android/macos/linux`。
> **每台设备一个 token，绝不能共用**（共用会导致两台设备挤在同一张卡片、状态互相覆盖）。

### 4.5 HTTPS（DNS-01，不依赖入站端口）

1. 从 ddns-go 配置里取 dynv6 API token
2. 写 DNS-01 钩子 `/usr/local/bin/dynv6-acme.py`（调 dynv6 API v2 增删 `_acme-challenge` TXT 记录，并轮询确认传播）
3. 签发：

```bash
certbot certonly --manual --preferred-challenges dns \
  --manual-auth-hook   /usr/local/bin/dynv6-acme-auth.sh \
  --manual-cleanup-hook /usr/local/bin/dynv6-acme-cleanup.sh \
  --non-interactive --agree-tos --register-unsafely-without-email \
  -d example.dynv6.net
```

4. 自动续期：`certbot.timer`（systemd 每日两次），演练通过：

```
certbot renew --dry-run → all simulated renewals succeeded
```

> 踩坑记录：dynv6 API 域名解析要先强制 IPv4（`socket.getaddrinfo` 过滤 AF_INET），否则 Python 默认走 IPv6 会超时。

### 4.6 nginx 反向代理 + 安全加固

`/etc/nginx/sites-available/live-dashboard`（要点）：

```nginx
server {                       # 80：全部跳 HTTPS
    listen 80; listen [::]:80;
    server_name example.dynv6.net;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl; listen [::]:443 ssl;
    http2 on;
    server_name example.dynv6.net;

    ssl_certificate     /etc/letsencrypt/live/example.dynv6.net/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.dynv6.net/privkey.pem;
    add_header Strict-Transport-Security "max-age=31536000" always;
    add_header X-Content-Type-Options nosniff always;
    add_header Referrer-Policy no-referrer always;

    limit_conn ld_conn 24;                                     # 每 IP 并发连接上限

    location ^~ /.well-known/acme-challenge/ { allow all; }    # ACME 例外
    # 扫描器特征路径 → 444（直接断连，不返回任何内容）
    location ~* /(\.(env|git|svn|hg|aws|ssh|ds_store)|wp-admin|wp-login|wp-content|wp-includes|wordpress|phpmyadmin|pma|adminer|xmlrpc\.php|actuator|vendor/|cgi-bin|shell|backup|dumps?|admin\.php) { return 444; }
    location ~* \.(env|git|svn|bak|old|orig|sql|sqlite|ini|conf|log|yml|yaml|pem|key)$ { return 444; }
    location ~* \.(php[0-9]?|phtml|asp|aspx|jsp|jspx|cgi|pl|rb|py|sh|bash|exe|dll|so|bat|cmd)$ { return 444; }

    location /api/report {                                     # 上报接口单独放宽
        limit_req zone=ld_api burst=60 nodelay;
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    location / { limit_req zone=ld_site burst=60 nodelay; proxy_pass http://127.0.0.1:3000; … }
}
```

`/etc/nginx/conf.d/ld-limit.conf`：

```nginx
limit_req_zone  $binary_remote_addr zone=ld_site:10m rate=20r/s;
limit_req_zone  $binary_remote_addr zone=ld_api:10m  rate=30r/s;
limit_conn_zone $binary_remote_addr zone=ld_conn:10m;
limit_req_status 429;
limit_conn_status 429;
```

实测结果：正常路径全 200（`/`、`/api/*`、`/favicon.ico`、模块 zip、`_next` 静态资源），
扫描路径（`/.env`、`/wp-login.php`、`/config.php`、`/a.jsp`、`/db.sql` …）全部 CLOSED，
连打 120 次触发 `429×14`，3 秒后自动恢复。

## 5. 手机端：KernelSU 上报模块

### 5.1 模块结构

```

├── config.sh              # 全部配置（含 token、间隔、隐私模式）

├── action.sh              # KernelSU「操作」按钮 → 一键切换隐私模式
├── uninstall.sh           # 卸载时杀进程 + 清理 /data/adb/live-dashboard
├── bin/sqlite3-arm64      # 静态编译的 aarch64 sqlite3（2.3 MB，零动态依赖）
└── META-INF/…             # 安装脚本（兼容 Magisk/KernelSU）
```

运行状态目录 `/data/adb/live-dashboard/`：`reporter.log`（日志）、`reporter.pid`、`privacy`（隐私模式标记文件）、`ca.pem`（如用自带 curl）。

### 5.2 为什么不用官方 App 的无障碍方案

官方 Android App 的前台识别有三级回退，**无障碍快照优先且有效期长达 12 小时**：

```kotlin
detectCurrentApp(accessibilitySnapshotMaxAgeMs = 12 * 60 * 60 * 1000L, …) {
    detectFromAccessibility(...)?.let { return it }   // ① 12 小时内命中就返回
    if (!hasUsageAccess()) return null
    detectFromUsageEvents(...)                        // ②
    detectFromUsageStats(...)                         // ③
}
```

后果：MIUI 的**游戏加速/游戏工具箱**（`com.miui.securitycenter`）抢占前台后，快照就卡在"手机管家"，
12 小时内都不会回退到更准的 `UsageStats` —— 面板一直显示"手机管家"而不是游戏名。

**模块版方案**：直接 `dumpsys` 问 ActivityManager 谁在前台，游戏/模拟器一样能识别：

```sh
dumpsys activity activities | grep -m1 -E 'topResumedActivity|mResumedActivity' \
  | tr ' ' '\n' | grep -m1 -E '^[A-Za-z0-9_][A-Za-z0-9_.]*/' | cut -d/ -f1
# 兜底：dumpsys window | grep mCurrentFocus
```

附带收益：`dumpsys power`（息屏判定）、`dumpsys battery`（电量/充电）、`dumpsys media_session`（音乐）全部免费拿到。

### 5.3 健康数据读取

手机上没有 `sqlite3` 命令，因此模块内置了**服务器上交叉编译的静态 aarch64 sqlite3**：

```bash
# 在服务器上（Debian）准备：
apt-get install -y gcc-aarch64-linux-gnu tcl qemu-user-static
apt-get source sqlite3 && cd sqlite3-3.46.1
./configure && make sqlite3.c && make sqlite3        # 生成合并源码
aarch64-linux-gnu-gcc -O2 -static -DSQLITE_OMIT_LOAD_EXTENSION -DSQLITE_THREADSAFE=0 \
  -o sqlite3-arm64 shell.c sqlite3.c -lpthread -ldl
qemu-aarch64-static ./sqlite3-arm64 "select 1+1;"   # 上机前先验证
```

读取的数据源与语义映射（**注意单位**）：

| 面板类型 | 数据源 | SQL 要点 | 单位/时间戳 |
|---|---|---|---|
| `steps` | `/data/data/com.miui.rom/databases/Steps.db` → `StepsTable` | `sum(_steps)` 按本地日期聚合 | count；当天 00:00 |
| `height`/`weight`(档案) | `com.mi.health/databases/fitness_user` → `user_info_profile` | `height, weight` | cm / kg；当天 00:00 |
| `heart_rate` | `…/databases/<账号>/cn/fitness_data` → `hr_record` | `json_extract(value,'$.bpm')` 按**小时平均** | bpm；整点时间戳 |
| `sleep` | 同上 → `sleep_segment` | `json_extract(value,'$.duration')`（**分钟**） | min；入睡/起床时间 |
| `oxygen_saturation` | 同上 → `spo2_record` | `json_extract(value,'$.spo2')` | %；当天 |
| `weight`(实测) | 同上 → `weight_item_record` | 最新一条 `weight>0` | kg；称重时间 |

**三个必须记住的坑**：

1. **单位**：前端 `formatValue()` 里 `sleep`/`exercise` 的值是**分钟**（`Math.floor(v/60)`），`distance` 是**米**。发成"小时"会显示成 `0h 7m`
2. **WAL**：读 App 的库必须把 `db`、`-wal`、`-shm` **三件套一起**处理，否则读到的是旧值/空值
3. **时区串要补零**：`+8:0` 不是合法 ISO → JS 解析成 Invalid Date → 服务端会静默丢弃每一条（返回 `inserted: 0` 但 HTTP 200）

## 7. 隐私模式

### 7.1 行为

开启后模块只发 `app_id=private`：**不报应用名、不报窗口标题、不报音乐（歌名/歌手）**，只保留电量。
服务端把 `private` 映射为「隐私模式 · 现在不方便说喵~」。
健康数据不受影响（它是另一条链路）。

### 7.2 三种开启方式

### 8.1 字段与单位约定（重要）

```jsonc
// POST /api/report
{
  "app_id": "com.tencent.mm",       // 必填
  "window_title": "…",              // 可选；服务端按隐私分级处理后只存 display_title，原文不落库
  "timestamp": "2026-10-03T09:00:00Z",  // 可选，±5 分钟内有效，否则用服务端时间
  "extra": {                        // 可选，白名单字段
    "battery_percent": 87, "battery_charging": true,
    "music": { "title": "…", "artist": "…", "app": "…" }
  }
}

// POST /api/health-data
{ "records": [
  { "type": "steps",  "value": 199,  "unit": "count", "timestamp": "2026-10-03T00:00:00+08:00" },
  { "type": "sleep",  "value": 400,  "unit": "min",   "timestamp": "2026-10-03T00:30:00+08:00",
                      "end_time": "2026-10-03T07:10:00+08:00" },
  { "type": "heart_rate", "value": 78, "unit": "bpm", "timestamp": "2026-10-03T15:00:00+08:00" }
]}
```

| type | 单位 | 值语义（**前端如何显示**） |
|---|---|---|
| `sleep` / `exercise` | `min` | **分钟** → `Math.floor(v/60)` 显示 `Xh Ym` |
| `distance` | `m` | **米** → `v/1000` 显示 km |
| `steps` | `count` | 整数，千分位 |
| `heart_rate` / `resting_heart_rate` | `bpm` | 整数；≥2 个点会画折线图 |
| `oxygen_saturation` | `%` | 整数 |
| `weight` | `kg` | 小数一位 |
| `height` | `cm` | 整数 |
| 其余合法类型 | — | `active_calories`/`total_calories`/`body_temperature`/`blood_pressure`/`heart_rate_variability`/`respiratory_rate`/`blood_glucose`/`hydration`/`nutrition` |

服务端校验：18 种合法 type、每批 ≤500 条、`unit` ≤20 字符、时间戳必须能解析，非法项**静默跳过**（所以务必检查响应里的 `inserted` 数量）。

### 8.2 探活为什么不发假数据

早期版本用 `POST /api/report {"app_id":"reporter-probe"}` 探活，会在时间轴留下垃圾行；
现改为 `GET /api/consent`（要鉴权、不写数据），并清掉了历史垃圾行。

## 9. 数据模型与保留策略

SQLite：`/opt/live-dashboard/data/live-dashboard.db`（WAL 模式，`busy_timeout=5000`）

| 表 | 作用 | 关键字段 | 保留 |
|---|---|---|---|
| `activities` | 活动时间轴 | `device_id, app_id, app_name, display_title, title_hash, time_bucket, started_at` | **7 天自动清理**（每小时一次） |
| `device_states` | 设备当前状态 | `device_id(PK)`、`app_id/app_name/display_title`、`extra(JSON)`、`last_seen_at`、`is_online` | 常驻；60 秒无上报即 `is_online=0` |
| `health_records` | 健康数据 | `(device_id,type,recorded_at,end_time)` 唯一 → **UPSERT 原地更新** | **无过期策略**（持续增长） |
| `device_consents` | 显式同意 | `activity_reporting`、`health_reporting`、`granted_scopes` | 常驻 |

其他实现细节：

- `window_title` 列**永远写空字符串**；实际展示用 `display_title`（由隐私分级从标题提取）
- 隐私分级三档 `show / browser / hide` + 独立的 SECRET 集合（银行/密码管理器等整应用匿名化为"私密应用"）
- **默认档是 `show`**：未收录的应用会**原样展示窗口标题**（README 说的"标题原文永不落库"仅在"`window_title` 列"意义上成立）
- 启动时会清理"未在 `DEVICE_TOKEN_N` 中配置的设备"的全部数据 —— **删 token = 删历史**，操作前先备份

## 11. 安全加固

| 措施 | 状态 |
|---|---|
| HTTPS（Let's Encrypt，ECDSA，DNS-01 自动续期） | ✅ |
| HSTS / `X-Content-Type-Options` / `Referrer-Policy` | ✅ |
| 全站限流（20 r/s + burst 60）与 `/api/report` 独立配额（30 r/s） | ✅ |
| 每 IP 并发连接上限 24，超限 429 | ✅ |
| 扫描器路径与脚本类扩展名 → 444 | ✅ |
| 上报鉴权 Bearer Token（每设备独立） | ✅ |
| 窗口标题不落库 + 隐私分级 + 隐私模式 | ✅ |
| 健康接口鉴权 | ❌ **未做**（见下） |

### ⚠️ 唯一未解决的风险：健康数据公网明文可读

`/api/health-data` 与 `/api/current`、`/api/timeline` 一样**无鉴权**。域名已在公网可达，
任何拿到域名的人 `curl https://example.dynv6.net/api/health-data?date=…&device_id=phone-a`
即可读走心率/睡眠/体重。

**建议方案**：给健康接口加访问口令（后端校验 `?key=` 或请求头，前端首次输入后存 localStorage）。
工作量约 15 分钟。**待决策。**

### 公网暴露的客观事实

- 签发 Let's Encrypt 证书会把域名写进**公开的 CT 日志**，几分钟内就有机器人来抓
- 实测：DigitalOcean 主机（headless Chrome）与 `2a05:9403::/5f9`（双 UA 的 URL 检测机器人）各访问 4 次，
  **只取了首页与 favicon、没碰任何 `/api/*`**（SPA 数据靠 JS 拉取，它们没执行 JS）
- 结论：站点被发现无法避免；加固后扫描类流量会被 444 直接掐断

## 14. 应用使用时长与屏幕时间统计

### 14.1 数据从哪来（为什么不能像运动健康那样读库）

最初的想法是"跟小米运动健康一样直接读它的库"，实测**行不通**：

| 检查项 | 实测结论 |
|---|---|
| `/data/system/usagestats/0/` | **空目录**（Android 16 把 usage 数据放内存，不落盘） |
| 系统里的"数字健康/屏幕时间"包 | **不存在**（只有 `com.miui.screenrecorder` 录屏、`com.xiaomi.digitalkey` 数字车钥匙、`com.miui.screenshot` 截屏） |
| 手机管家 / 功耗管理的库 | `app_predict_data.db`、`powerchecker.db`、`cloud_configure.db`，**没有任何屏幕时长表** |
| `dumpsys usagestats` 尾部的 `totalTimeUsed` / `totalTimeVisible` | 是**全生命周期累计**（抖音 `256:19:53`），不是当天口径 |

→ **MIUI 的「屏幕使用时间」没有可读数据库**，它和我们读的是同一个源（`UsageStatsManager`）。
只能自己从 `dumpsys usagestats` 的**事件流**里算，好在口径能做到与系统一致。

### 14.2 三个统计口径

| 口径 | 算法 | 今日实测 |
|---|---|---|
| 亮屏时长 | `SCREEN_INTERACTIVE` → `SCREEN_NON_INTERACTIVE` 配对 | **373 分 = 6.22 h** |
| 解锁时长 | `KEYGUARD_HIDDEN` → `KEYGUARD_SHOWN` 配对 | **364 分 = 6.07 h** |
| 各 App 前台时长 | `ACTIVITY_RESUMED` → `PAUSED/STOPPED` 配对（+ 熄屏恢复 + 保留"最后已知前台应用"） | **345 分 = 5.75 h** |

**与手机「设置 → 屏幕使用时间」的显示一致**（MIUI 取整/刷新滞后会有几十分钟差异）。
对账方法：`各 App 合计 + 排除项 ≈ 亮屏时长`（实测差 28 分 = 桌面/系统界面，符合预期）。

### 14.3 算法要点（5 个坑，全是实测踩出来的）

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| 1 | `days()` 返回**儒略日**而非 Unix 天数 | "只算今天"的过滤完全失效，报的是最近 24 小时 | 结果 `- 2440588` |
| 2 | **墙上时间 vs 真实 epoch 混用** | 今日基准多减了 8 h 偏移，"今天"从昨天 16:00 起算 | 今日基准用 `((NOW+OFF)/86400)*86400`（**不减** OFF） |
| 3 | dump 的事件**不是按时间排序、且有重复行**（实测 867 行重复） | 同一段时长被重复累加，亮屏虚高到 12.4 h | `sort -u` 之后再配对 |
| 4 | `ACTIVITY_STOPPED` 后清空"当前应用" | 屏幕仍亮但前台是系统 UI 时计时中断，少算约 10 h | 保留 `cur`，只在新 `RESUMED` 时替换 |
| 5 | `PAUSED` 后计时起点被清零且未重置 | 同一应用持续在前台却不再累计（游戏的 124 分钟全丢） | `flush` 后 `st=ts`，继续计时 |

### 14.4 采集与上报

模块每 `USAGE_INTERVAL`（默认 600 s）执行一次：

```sh
# 提取事件（两种：带 package 的算"各 App"，不带的算亮屏/解锁）
dumpsys usagestats | sed -n 's/.*time="\([0-9-]*\) \([0-9:]*\)" type=\([A-Z_]*\) package=\([A-Za-z0-9_.]*\).*/\1 \2 \3 \4/p' | sort -u
# …按 §14.3 的要点在 awk 里配对…

POST /api/usage
{"date":"2026-10-03","screen_minutes":373.3,"unlocked_minutes":364.1,
 "records":[{"app_id":"com.tencent.mm","minutes":85.2},{"app_id":"com.tencent.tmgp.dfm","minutes":124.8}, …]}
```

落库两张表：`usage_stats(device_id, date, app_id, app_name, minutes)` 与
`screen_time(device_id, date, screen_minutes, unlocked_minutes)`（同为 UPSERT，**同一天重复上报是覆盖不是累加**）。

## 15. 事件监听与本机通知（路线 A）

### 15.1 目标与边界

- **只在我这边收到通知**：事件内容不上面板、不在公网 JSON 里，`GET /api/events` 必须带设备 token（无 token → 401）
- **被动监听**：对方设备照常上报，服务端只读它已经上报的状态，**不向它下发任何指令**
- 目前监听设备：`WATCH_DEVICES=phone-b`（手机B）；监听的设备列表可随时改

### 15.2 链路

```
设备上报 → 服务端更新 device_states
                ↓  watcher（每 WATCH_INTERVAL=15 s）
        与上一次快照对比，检测「变化」→ 写入 events 表
                ↓  GET /api/events?since=<id>（Bearer token）
    我的手机模块（每 EVENT_INTERVAL=30 s 轮询）
                ↓  cmd notification post -S bigtext
   系统通知栏（渠道 shell_cmd，importance 3）
```

### 15.3 监听的事件

| kind | 触发条件 | 通知示例 |
|---|---|---|
| `online` / `offline` | 设备上线 / 离线（60 s 无上报判离线） | 🔵 手机B 上线了 · 当前：微信 |
| `app` | 前台应用变化（`idle`/`unknown`/`private` 不发） | 📱 手机B 打开了 抖音 |
| `charging` / `unplugged` | 插上 / 拔掉充电器 | 🔋 手机B 开始充电 · 当前电量 57% |
| `battery_low` | 电量**首次**跌破阈值（回升 5% 后才重新武装） | 🪫 手机B 电量偏低 · 剩余 18% |
| `privacy` | 从普通状态进入隐私模式 | 🔒 手机B 进入隐私模式 |

### 15.4 配置

服务端 `/etc/live-dashboard.env`：

```sh
WATCH_DEVICES=phone-b       # 要监听的设备（逗号分隔；加上 phone-a 可连自己也监听）
WATCH_BATTERY_LOW=20           # 低电量阈值 %
WATCH_COOLDOWN=60              # 同一设备两次"打开应用"通知的最小间隔（秒），防刷屏
WATCH_STATE_COOLDOWN=600       # 上线/离线的抖动抑制窗口（秒）；她手机上的官方 App 被 MIUI 反复杀，
                               # 实测 42 分钟抖动出 17 条事件（每 2.5 分钟一条），必须抑制
WATCH_INTERVAL=15              # 检测间隔（秒）
```

**抖动抑制机制**：`events` 表有 `notify` 列。
watcher 在写入事件前，查同设备同类型的上一条事件，若在冷却窗口内 → `notify=0`（**事件照样入库，只是不通知**）；
`GET /api/events` 返回该字段，模块遇到 `notify=0` 只写日志不弹通知（日志标记 `[静默]`）。
实测：`应通知 20 条 / 已静默 4 条`，若没抑制本该弹 24 条。

模块 `config.sh`：`EVENT_ENABLE` / `EVENT_INTERVAL`（见 §5.4）。

### 15.5 实现要点

- **首次运行只对齐游标、不弹历史**：`events.since` 不存在时把游标推到当前最大 id，避免开机被几十条历史通知淹没
- **冷却 + 抖动抑制**：`app` 事件按 `WATCH_COOLDOWN`（默认 60 s）、上线/离线按 `WATCH_STATE_COOLDOWN`（默认 600 s）判定；窗口内的重复事件写库但标 `notify=0`，模块只记日志（`[静默]`）
- **`idle` 过滤**：息屏上报的 `app_id=idle` 不是"打开了应用"，watcher 里用 `SKIP_APP` 挡掉
- **通知渠道**：`cmd notification post` 走系统 `shell_cmd` 渠道，通知栏来源显示为「Shell 命令」，importance=3（通知栏可见，**不弹横幅**）
- **⚠️ 必须以 shell（uid 2000）身份发送**（本节最大的坑，见下）
- **私有性**：事件只落本机 SQLite，前端没有任何入口；`/api/events` 无 token 直接 401

### 15.5.1 通知发不出去的真正原因（2026-10-03 排查全过程）

症状：事件在服务端正常产生、模块日志也显示收到了（`event#9/#10/#11`），**但通知栏什么都没有**。

| 排查步骤 | 结论 |
|---|---|
| ① 发一条带唯一 tag 的通知，再 `dumpsys notification` 搜 tag | 搜不到 → 通知**从未进入系统** |
| ② 截屏看通知栏 | 只有「应用更新」「USB 调试」，确认没显示 |
| ③ `dumpsys` 里 shell 的 NotificationRecord 数 | **0 条** |
| ④ **`logcat` 抓现场** ✅ | 真相在这里 ↓ |

```
E NotificationService: Cannot fix notification
E NotificationService: android.content.pm.PackageManager$NameNotFoundException: root
    at NotificationManagerService.fixNotification(NotificationManagerService.java:8991)
    at NotificationShellCmd.doNotify(NotificationShellCmd.java:694)
```

**根因**：模块以 **root** 身份执行 `cmd notification post`，系统用调用者 uid 反查包名得到 **`"root"`**——
而这个包名根本不存在 → `fixNotification` 抛 `NameNotFoundException` → 通知被静默丢弃。
（**不是** MIUI 的通知过滤，一开始的猜测是错的。）

**修法**：降权到 shell（uid 2000）再发，包名就变成 `com.android.shell`：

```sh
# 方式一：KernelSU 的 su 支持数字 uid
su 2000 -c 'cmd notification post -S bigtext -t "标题" 标签 "正文"'
# 方式二：模块里用 busybox 降权（参数不经 shell，中文/emoji 更安全）
"$BUSYBOX" setuidgid 2000 /system/bin/cmd notification post -S bigtext -t "标题" 标签 "正文"
```

验证（`logcat` 里 `Cannot fix notification` 出现 0 次）：

```
dumpsys notification → pkg=com.android.shell ... tag=ld-15
   android.title = "🔵 手机B 上线了"      android.text = "当前：微信"
dumpsys notification → pkg=com.android.shell ... tag=ld-16
   android.title = "📱 手机B 打开了 微信"  android.text = "时间 19:01:04"
```

**推论**：KernelSU 模块自带 root，用 `su 2000` 降权即可发原生通知，**不需要额外装 App，也不需要 LSPosed**。

**已知限制**：
- 锁屏界面默认不显示 shell 的通知（`mLockscreenVisibility=-1000` + MIUI 策略），解锁后通知栏可见
- importance=3 → 不弹横幅；想要"弹窗提醒"需把该渠道重要性提到 4（目前只能靠 MIUI 设置里手动改，或用 LSPosed hook）

### 15.6 实测记录

| 步骤 | 证据 |
|---|---|
| 模拟对方设备上线（用她的 token 发一次上报） | 服务端产生 `[1] online 上线了`、`[2] app 打开了 微信` |
| 模块轮询并弹通知 | 模块日志 `event#3 [app] …`、游标从 2 → 3；`dumpsys notification` 里出现 `com.android.shell` 记录 |

| **通知终于可见**（v1.14） | 降权到 shell uid 后，`dumpsys notification` 出现 `tag=ld-15/ld-16`，标题正文正确（含 emoji） |

## 16. 已知限制与注意事项

1. **仅 IPv6 对外**：没有公网 IPv4，访客必须支持 IPv6（手机 4G/5G 一般可以，部分公司网络不行）
2. **健康数据公开可读**：见 §11，待加口令
3. **默认放行未收录应用的窗口标题**：上游隐私分级是黑名单式（`?? "show"`），想更保守需要改源码把兜底改成 `hide`
4. **`health_records` 无过期策略**：目前量很小，长期需要加清理
5. **小米运动健康必须保留**：模块从它的库读手环数据；删了它健康链路就断了
6. **手环数据依赖 App 同步**：手环不戴/不同步 → 心率睡眠停更（步数由手机自记，不受影响）
7. **MIUI 杀后台**：官方 App 常被判离线；root 模块（KernelSU 服务）不受影响
8. **首页字体**：前端 CSS `@import` 了 Google Fonts，国内浏览器加载不到会回退系统字体（仅观感差异）
9. **依赖 GitHub 的升级路径**：`github.com` 被墙，升级源码要走 `codeload.github.com`；Bun 升级走 npm
10. **上游 fork 漂移**：本项目基于上游 `Monika-Dream/live-dashboard` 的 main（2026-07），改了两处源码（DatePicker、/api/diag），升级上游时需重新套用
11. **使用时长只有"上线之后"的数据**：`usage_stats` 从功能上线当天开始记录；系统侧的事件流最多回看 24 小时，**补不了更早的历史**
12. **事件通知依赖我的手机在线**：路线 A 靠"我的手机轮询"，手机离线/模块被停时会漏掉通知（事件仍在库里，恢复后可补看）
13. **亮屏/解锁与 MIUI 显示可能有几十分钟差异**：MIUI 的刷新与取整策略不同；自检标准是「各 App 合计 ≈ 亮屏时长」
14. **`events` 表没有过期策略**：目前量很小，长期需要加清理（`activities` 已有 7 天自动清理）
